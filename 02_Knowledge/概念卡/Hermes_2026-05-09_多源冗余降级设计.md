# 多源冗余降级设计

**背景**
2026-05-09 财经20:30推送中，X API超时后系统自动切换至东方财富+界面+新浪财经API，最终成功推送。这验证了多源冗余设计的有效性——但财经08:00在所有数据源同时离线时，系统选择了诚实降级而非降级捏造。

**核心洞察**

## 多源冗余的三个层级

| 层级 | 策略 | 适用场景 |
|------|------|---------|
| L1 主备切换 | 主数据源失败时自动切换备用 | X API超时 → 东方财富 |
| L2 多源并行 | 多个源并行获取，去重合并 | 财经多频道整合 |
| L3 降级诚实 | 所有源不可用时，诚实告知无法推送 | 数据源全面离线 |

## 设计原则

**优先级：L1 > L2 > L3，never L0（捏造内容）。**

财经08:00案例中，所有外部财经数据源（NewsAPI、Yahoo Finance、Reuters、WSChina、Investing.com）同时不可用，返回速率限制或超时。模型选择"诚实告知无法推送"，这是正确的降级路径。

**关键判断标准：** 当数据源返回错误而非返回空数据时，模型无法区分"暂时不可用"和"永久无数据"，所以宁可诚实告知也不编造。L3降级不是失败，是正确的设计选择。

## 实现框架

def fetch_with_fallback(query):
    sources = [
        ("x_api", xurl_search),

    results = []
    for name, fn in sources:

            r = fn(query)

    if results:

**对Jerry的意义**
多源冗余设计保证了Cron任务在单数据源故障时仍能完成。财经20:30证明了这一点。但L3降级（诚实告知）同样重要——宁可让用户知道"今天没有数据"，也不要生成看似真实但实际捏造的内容。建立数据源健康度追踪更重要。

**延伸思考**
可以给每个数据源打"可用性评分"，长期追踪后可以预判哪些数据源在哪些时段容易故障，提前切换。例如X API在凌晨可用性低，可以将凌晨的财经任务默认切换到东方财富。

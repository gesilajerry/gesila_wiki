# 小红书自动化脚本Bug定位：UnboundLocalError陷阱

**背景**
2026年5月6日，xhs-video-gen任务执行时报错UnboundLocalError，最终定位原因是`scene_prompts`变量定义在代码第268行，但在第219行已被调用。Python函数作用域规则导致内侧函数无法"看到"尚未执行的外部变量定义，引发运行时错误。

**核心洞察**
UnboundLocalError是Python新人最常踩的"隐形陷阱"之一，根源在于Python的"先赋值后使用"作用域解析顺序——当函数内部有任何赋值操作时，Python将该变量视为局部变量，即使外部有同名全局变量也不再隐式引用。

本案中，`scene_prompts`变量在第268行通过列表推导式赋值，但在第219行（循环中）被引用时，Python已经将`scene_prompts`标记为函数局部变量。由于赋值语句尚未执行，读取时发现是"未赋值的局部变量"，遂抛出UnboundLocalError。

修复方法：在函数开头添加`global scene_prompts`（如果确实是全局变量），或在调用前完成赋值并将变量作为参数传入。更好的设计是避免使用跨越大幅代码的隐式全局状态，改用数据类或配置文件集中管理常量。

**对Jerry的意义**
这个bug的发现过程（用print调试→定位报错位置→溯源变量定义）是自动化脚本调试的典型范式。Jerry的Hermes系统涉及多个自动化脚本（新闻推送、视频生成、知识提炼等），这类脚本通常由cron定时触发、没有交互界面，Bug定位完全依赖日志。养成在关键路径添加结构化日志（记录执行步骤和关键变量值）的习惯，是保障无人值守脚本稳定性的关键。

**延伸思考**
代码审查层面，防止UnboundLocalError的最佳实践是：
1. 变量定义和使用尽量靠近，避免大幅度的代码跳跃
2. 使用类型提示（typing）让IDE能静态检测未定义变量
3. 对于跨函数共享的配置，使用dataclass或pydantic集中管理，通过参数显式传入
4. 对cron任务脚本，在关键节点写入执行状态日志（可以用Python的logging模块输出到文件），这样任务失败时可以快速定位断点而非盲猜

# 8GB内存Mac本地LLM部署铁律

## 背景

2026-07-31 在 8GB 统一内存 Mac 上实测 Gemma 3 4B / Qwen3 8B / Qwen3 4B 四款 GGUF 模型，踩遍 Metal OOM、速度崩盘等坑后总结出的硬件边界规律。

## 核心洞察

**洞察1：内存预算公式** — 8GB 统一内存可容纳的模型 = 权重(Q4_K_M) + KV cache + 系统占用。4B 权重约 2.5GB 可全 GPU 跑；8B 权重约 5GB，加上 KV cache 必爆 8GB（实测报错 `ggml_metal_synchronize: error: command buffer 0 failed with status 5` / `Insufficient Memory 00000008`）。

**洞察2：-ngl 层数三态** — 全 GPU（-ngl 99）OOM；-ngl 超过模型总层数（Qwen3 8B 共 36 层，-ngl 40）会被 clamp 回全 GPU 依然 OOM；只有 -ngl 18（GPU/CPU 各半）能跑起来，但速度崩到 3 t/s 不可用。**结论：8B 模型不适合 8GB 机器，无论怎么调参。**

**洞察3：上下文长度是隐藏内存杀手** — -c 12288 + 4 slots 的 KV cache 占用巨大；8GB 机器建议上下文 ≤2048。大 context 还会拖慢 prompt 处理（11508 tokens 时实测 prompt 125 t/s → 随长度衰减）。

**洞察4：llama.cpp v10180 参数变更** — `--mlock` / `--no-mmap` 已废弃（DEPRECATED），改用 `--load-mode mlock` / `--load-mode mmap`。

**洞察5：量化选择** — Q4_K_M 是 8GB 机器的甜点位；Q8_0/F16 仅适合内存充裕场景。

## 对Jerry的意义

8GB Mac 是主力硬件，这套边界规律直接决定了本地模型选型：**只选 4B 级 Q4_K_M 量化模型**，不要浪费时间尝试 8B。后续任何本地 agent 方案（Trae/IDE 接入）都以此为前提，避免重复踩 OOM 坑。

## 延伸思考

统一内存架构下 GPU/CPU 共享带宽，-ngl 分层本质是在"显存容量"和"推理速度"之间做交易。若未来升级 16GB+ 内存，8B 模型可全速运行，届时本铁律的上限自动放宽。

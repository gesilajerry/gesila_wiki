# mmx CLI环境依赖失效的静默失败陷阱

**背景**
2026-05-12，xhs-vangogh-r1和r2两个流水线任务执行时，xhs-vangogh-r2因`mmx`命令不可用而静默失败：脚本exit_code=0正常退出，但实际没有生成任何图片；而xhs-vangogh-r1在同一环境中执行成功（图片生成正常）。排查后发现`mmx`不在PATH中，且pip/npm/conda/go等包管理器均无法安装。

**核心洞察**
这个案例暴露了CLI工具环境依赖的核心风险：**本地开发环境与cron执行环境的差异不会被任何报错捕获**。具体问题包括：

第一，cron任务通常在最小化环境（无GUI、无扩展PATH、无用户profile）中执行，许多在开发终端中可用的命令在此环境下完全不可见；

第二，Python脚本调用`subprocess.run('mmx ...')`时，如果命令不存在，subprocess不会自动报错（取决于调用方式），且可能静默返回空结果而非抛出异常；

第三，同一脚本在开发环境和cron环境中的行为不一致（r1成功/r2失败），说明r1和r2可能调用了不同的内部路径，或者r2的执行环境与r1有细微差异。

**正确应对方法**
1. **环境自检作为第一步**：在脚本开头添加环境可用性检查，对依赖的每个CLI工具执行`which`或`shutil.which`验证，不可用则立即报错退出而非静默继续；
2. **依赖清单文档化**：在技能文档或脚本注释中明确列出所有外部CLI依赖及其安装方式，避免维护者不清楚依赖关系；
3. **结果校验机制**：对于生成型任务（图片/音频/文档），在脚本结尾添加输出校验——检查文件是否真实生成、大小是否合理，而非仅依赖subprocess的exit_code；
4. **CI/CD式预检**：在cron任务执行前，先用独立探针任务（早5分钟）验证环境可用性，发现问题提前告警。

**对Jerry的意义**
这个陷阱在Hermes的多个流水线中普遍存在（blog-publisher依赖curl，xhs-vangogh依赖mmx，minimax-search依赖mmx）。每次新环境部署或系统更新后，必须重新验证所有CLI依赖的可用性。建议建立"环境就绪检查"的标准流程，作为所有依赖CLI的cron任务的标准前置步骤。

**延伸思考**
这个问题本质上是"开发环境与生产环境一致性问题"的子集。更系统的解法是使用Docker或虚拟环境打包完整依赖（如`pip freeze` + `requirements.txt`），确保cron执行环境与开发环境完全一致。但对于macOS原生环境（Homebrew路径、conda路径等），Docker方案有时反而增加复杂度。折中方案是：在脚本注释中明确标注"已验证环境：macOS 14.x + Homebrew + Python 3.x"，并在新系统部署时更新该注释。

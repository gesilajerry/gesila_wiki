# 方法论：Hermes多安装路径更新陷阱与正确流程

## 背景

2026-08-05 更新 Hermes Agent（v0.18.2 → v0.20.0）时发现：机器上存在**两套 Hermes 安装**——`~/.hermes/hermes-agent`（另一套，之前误更新过）与 `/Volumes/256G/mywork/hermes`（**实际运行 gateway 的安装**）。`--prune` fetch 后才发现 HEAD 落后 origin/main **5353 个提交**（v2026.7.7.2 → v2026.8.3 之后持续更新），之前那次"更新"实际没生效。

## 核心洞察

**洞察1：更新前必须确认 gateway 实际运行目录。** 安装路径 ≠ 运行路径。用 `hermes --version` 输出中的 `Install directory:` 确认当前 gateway 使用的安装，或 `ps aux | grep hermes` 查实际进程路径。更新错目录 = 白更新。

**洞察2：fetch 后核对落后提交数。** `git fetch --prune` 后执行 `git rev-list --count HEAD..origin/main` 确认落后量；`git describe` 对照版本号。若落后数千提交说明之前从未真正同步。

**洞察3：本地定制文件更新前必须备份，更新后必须验证。** 更新前 `cp adapter.py /tmp/adapter.py.bak`；更新后 `grep -c` 验证关键定制标记（如 NO_PROXY 绕过、extra_ua_tags）仍在。`hermes update --yes` 会同步 bundled skills（"↑1 updated, ~4 user-modified"），并重建 Web UI、自动重启 dashboard。

**洞察4：通过代理更新 git 仓库。** 国内网络更新 GitHub 仓库时：`export http_proxy=http://127.0.0.1:7890 https_proxy=http://127.0.0.1:7890 && hermes update --yes`（注意 `-c` 是 git 参数不是命令前缀，不要写 `git -c ... hermes update`）。

## 对Jerry的意义

- 避免再次出现"更新了但没生效"的假成功：更新前后各跑一次 `hermes --version` 对照 Install directory；
- gateway 是 7/16 启动的旧进程，更新代码后**必须重启 gateway** 才能让飞书通道加载新版本（会短暂中断会话，需挑时机）；
- 可选优化：`hermes sessions optimize-storage` 释放约 0.8GB 会话存储。

## 延伸思考

多安装路径问题根源是历史部署分散（~/ 与 /Volumes/256G/）。长期建议：统一安装位置或建立符号链接，并在 MEMORY 中记录真实运行目录，避免每次更新都踩坑。

# 系统性故障复盘方法论：idle timeout 根因治理

**背景**
2026-05-09归档窗口内，idle timeout问题从偶发演变为系统性失败——凌晨至午后多个Cron任务连续超时，整体成功率仅36%。问题在多次归档中已被记录但配置始终未调整，导致问题持续恶化。

**核心洞察**

## 1. 问题分类矩阵

| 故障类型 | 特征 | 根因方向 |
|---------|------|---------|
| idle timeout | 任务启动但模型无法在阈值内输出 | timeoutSeconds配置不足 或 模型资源不足 |
| NO_REPLY | Cron运行但模型快速返回空内容 | 任务描述配置错误 或 触发逻辑缺陷 |
| ECONNRESET | 搜索命令层面即失败（连接被重置） | 网络代理拦截 或 目标服务不可达 |
| 数据源离线 | 所有外部API同时不可用 | 上游服务问题，需降级策略 |

## 2. idle timeout 专项治理

**诊断流程：**
1. 确认超时发生的时段规律（凌晨高发？白天高发？）
2. 检查 `~/.hermes/cron/jobs.json` 中对应任务的 timeoutSeconds 配置
3. 确认模型提供商当前负载和可用性
4. 分析历史归档中同任务超时频率变化趋势

**配置调整原则：**
- minimax provider 的 `timeoutSeconds` 应设为 Cron任务预期最大耗时的 2-3 倍
- 凌晨时段（00:00~06:00）系统活跃度低，建议将此时段任务后移至白天
- 临时方案：`cronjob edit <job_id>` 调高该任务的 timeoutSeconds

**复盘记录标准化：**
每次归档应包含：
- 超时任务的 `job_id` 和执行时段
- 连续超时次数（判断是否"系统性"恶化）
- 建议的配置调整（具体参数名+目标值）

## 3. 多源冗余降级设计

**财经推送最佳实践：**
```
主数据源 → X API / 东方财富
         ↓ 超时/错误
备数据源 → 新浪财经 / 同花顺
         ↓ 全部失败
降级策略 → 诚实告知无法推送（不编造）
```

**原则：多源 > 单源 > 无数据。宁可诚实告知不可用，也不编造内容。**

## 4. NO_REPLY 专项排查

**特征**：Cron触发，进程运行，但模型返回空内容，9次连续失败。

**排查清单：**
1. 检查 `~/.hermes/cron/jobs.json` 中 Memory Dreaming 的任务描述是否正确
2. 验证任务 prompt 是否包含完整的系统指令
3. 查看 `~/.hermes/cron/runs/` 下对应 run 的 jsonl 日志，看模型实际输出
4. 尝试手动触发同一 prompt，确认是否为模型侧问题

**对Jerry的意义**
当前凌晨idle timeout成功率仅40%，持续恶化且配置未调整。需尽快执行两项修复：①调高timeoutSeconds至900s；②将凌晨任务（02:30财经、04:00 AI）后移至白天。同时Memory Dreaming 9次连续NO_REPLY需专项排查，不是偶发问题。

**延伸思考**
成功率36%意味着每天超过60%的自动化工作流处于失效状态。长期来看，需要建立"Cron健康度仪表盘"——实时追踪各任务成功率，触发阈值自动告警，而非依赖人工复盘发现。理想状态：成功率应维持在85%以上，失败任务应有明确的告警通知而非静默失败。

**标签**：Hermes × Cron运维 × 故障复盘 × 稳定性
